# S6: ACP 3.4.0 extension dispatch

Status: **verified** on 2026-10-25. The spike code lives only on local branch `spike/S6-acp-ext`, commit `2fdbd33f34`, in worktree `/tmp/zed-s6-acp-ext`; it is not merged into the M0 branch.

## Result

Use a type with `JsonRpcNotification` derived for the exact `_auth/status_update` method, registered through the same `Client.builder().on_receive_notification(..., on_receive_notification!())` API as existing `SessionNotification` and `CompleteElicitationNotification` handlers. A transparent wrapper around `serde_json::Value` retains the entire provider-defined payload. The handler must only decode/enqueue the notification; do not await another RPC inside the dispatch callback.

```rust
#[derive(Debug, Clone, serde::Serialize, serde::Deserialize,
         agent_client_protocol::JsonRpcNotification)]
#[notification(method = "_auth/status_update")]
#[serde(transparent)]
struct AuthStatusUpdate(serde_json::Value);

let builder = agent_client_protocol::Client.builder()
    .on_receive_notification(
        async |notification: AuthStatusUpdate, _connection| {
            // Enqueue notification.0 for the owning entity.
            Ok(())
        },
        agent_client_protocol::on_receive_notification!(),
    );
```

Call steering with `UntypedMessage::new`, keeping the complete wire method (including `_`). `ConnectionTo<Agent>::send_request(...).block_task().await` returns `serde_json::Value` for this request.

```rust
let response = connection.send_request(
    agent_client_protocol::UntypedMessage::new(
        "_session/steering",
        serde_json::json!({
            "sessionId": session_id,
            "prompt": [{"type": "text", "text": new_requirement}]
        }),
    )?,
).block_task().await?;
```

The payload above is the synthetic contract used by this transport spike. S6 proves routing and response handling; it does not validate a real adapter's steering schema or steering during a running prompt. T5.6 must confirm those provider-specific fields against pinned adapters before using them.

## Important API limits

- `schema::v1::ExtNotification`, `ExtRequest`, and `ExtResponse` hold `Arc<serde_json::value::RawValue>` payloads, but **do not implement** the builder/request traits individually. Passing them directly to `on_receive_notification` or `send_request` fails to compile.
- `schema::v1::AgentNotification` and `ClientRequest` provide enum fallbacks, but ACP 3.4.0's `impl_jsonrpc_*_enum!` parsing removes the first `_` from extension method names on receive. The exact-method notification derive avoids both that normalization and a catch-all handler that could intercept standard notifications.
- `UntypedMessage` also works as a catch-all receiver, but an exact method type is preferable alongside Zed's existing handlers.
- Extension routing does not need the `unstable` feature. The workspace nevertheless keeps its existing `schemars`, `unstable`, and `unstable_protocol_v2` features. Protocol v1 is used throughout this spike.
